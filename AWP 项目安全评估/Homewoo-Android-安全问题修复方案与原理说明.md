# Homewoo Android 安全问题修复方案与原理说明

**适用对象**：`com.sdmc.homewoo` Android 应用及其后端、Google/Firebase 云配置  
**编写日期**：2026-10-13  
**依据**：[Homewoo Android APK 安全静态评估报告](Homewoo-Android-APK安全静态评估报告.md)中的 8 项风险  
**前提**：为制定可执行方案，以下按“每项风险对应的最不利利用条件确实成立”设计修复；这**不是**对现有 APK 新增的漏洞验证结论。正式实施前应由客户端、后端和云平台负责人核对实际代码与配置。

## 如何理解“修复有效”

移动端程序和配置会交付到用户设备，攻击者可以读取、修改、重签并运行自己的版本。因此，客户端校验适合**减少意外暴露和提高攻击成本**，不能单独承担账号、对象权限、服务端秘密或生产环境隔离的最终保证。本文对每项问题都区分三层：

1. **消除根因**：让造成风险的路径不再存在，例如发布版不生成敏感日志、服务器不再信任全局客户端密钥。
2. **服务端强制**：即使客户端被改写，服务器仍拒绝越权、跨环境、过期或重放请求。
3. **验收和防复发**：用反例测试及发布检查确认修复在新版本里持续生效。

“保证不再出现”只能针对**明确的故障模式、受控系统和验收条件**作出。例如“服务端拒绝错误 `state` 的回调”可以被自动测试；“所有未来攻击都不可能成功”无法由一次修复或一次测试证明。下文的“完成判据”就是每项可核验的保证边界。

| 序号 | 假设成立的问题 | 必须阻断的结果 | 主要责任方 |
|---|---|---|---|
| 1 | 发布版日志实际含敏感报文 | 令牌/个人信息进入日志与诊断链路 | Android、后端、运维 |
| 2 | 外部路由或 OAuth 回调可绕过校验 | 未授权页面/对象访问、账号串绑 | Android、认证后端 |
| 3 | 正式包可切环境且环境身份混用 | 生产凭证流向测试环境或被测试环境接受 | Android、网关、认证后端 |
| 4 | 全体客户端共用可提取的 AES 秘密 | 提取一份 APK 即可伪造所有客户端材料 | Android、协议/后端 |
| 5 | 会话材料进入备份或设备迁移 | 恢复后得到可用凭证或敏感缓存 | Android、认证后端 |
| 6 | Google Key 缺少限制或 Firebase 规则过宽 | 未授权 API 消耗或云数据访问 | Google Cloud/Firebase 管理员 |
| 7 | 网络身份/应用完整性控制不足 | 弱 TLS、仿冒安装包或篡改请求被接受 | Android、网关、风控 |
| 8 | 存在非必要敏感权限 | 攻击或误用后可访问更多设备数据 | Android、产品、隐私负责人 |

## 1. 发布版 API 日志泄露请求、响应和凭证

### 问题原理

假设 `_logApiRequest`、`_logApiExchange` 在正式版把认证头、请求体或响应体写入 `logcat`、应用文件、崩溃上报或客服诊断系统。一次正常登录或刷新令牌就会产生**新的凭证副本**。这些副本不受原业务数据库的访问规则保护，可能被调试设备、预装特权组件、诊断收集人员或日志平台接触。即使日志只在异常时输出，异常对象的 `toString()` 也可能包含完整 URL、请求头和响应体。泄露令牌之后，攻击者是否能继续操作，还取决于令牌有效期、撤销和服务端授权。[Android 日志信息泄露指南](https://developer.android.com/privacy-and-security/risks/log-info-disclosure)

### 解决方案

1. **在日志产生点切断敏感数据**：正式构建的 HTTP 拦截器不读取、拼接或输出 `Authorization`、Cookie、签名、密码、验证码和完整请求/响应体；异常日志也只保存错误类别、接口模板、状态码、耗时和随机请求 ID。仅靠最后一道正则“涂黑”不可靠，因为未知字段、嵌套 JSON 和异常栈可能漏掉。
2. **定义允许字段清单**：为每类诊断事件定义固定字段结构，默认拒绝新字段；需要排障时用请求 ID 在有访问控制的服务端查询。开发版可启用详细日志，但不得与正式版共用开关、上报目标或真实用户凭证。
3. **检查所有副本**：统一规范客户端日志、崩溃平台、网关/服务端日志、APM、客服导出和离线诊断包。历史日志若已含真实令牌，按暴露范围删除/限制访问，撤销相应令牌并排查异常使用。
4. **降低泄露后的可用性**：访问令牌短时、刷新令牌可轮换和撤销；高风险写操作有幂等键/一次性挑战，且服务器每次校验用户和对象权限。

### 为什么有效

第一道控制在数据进入日志系统**之前**阻断复制，消除了这条泄露路径；字段白名单使未来新增 API 字段默认不会被打印。令牌短时和撤销机制只能限制已泄露凭证的使用时间，**不能替代停止记录凭证**。服务器的对象授权可阻止拿到某个用户令牌后访问其他用户的数据。

### 完成判据与边界

- 用测试账号走登录、令牌刷新、日历读写、设备绑定、支付成功/失败及异常请求；在 `logcat`、本地日志、崩溃/诊断平台和服务端日志中均检索不到测试令牌、认证头、密码、验证码、签名、完整个人数据或完整报文。
- 发布流水线对日志拦截器和诊断事件字段做检查；新增字段需要安全审查。
- 该判据能覆盖**受检查的日志链路和流程**；新的第三方 SDK 或后续新增上报路径仍须进入同一检查。

## 2. 外部路由与 OAuth 回调可能导致越权或账号串绑

### 问题原理

`MainActivity` 作为启动入口必须能被系统启动，其他 App 也可以通过 Intent 向导出的 Activity 提交自选 `route` 或 `homewoo://calendar/google/complete...` URI。**外部输入不因为进入 Flutter 就变可信**。若页面只依赖“用户正常点进来”判断权限，外部路由可能绕过页面入口；若 OAuth 回调只看授权码而不核对“是谁、在哪次授权请求中发起”，攻击者可能注入别人的授权结果。自定义 Scheme 还可能与其他 App 冲突，授权码被截获时需要 PKCE 限制其可兑换性。[Android 深链风险](https://developer.android.com/privacy-and-security/risks/unsafe-use-of-deeplinks)、[RFC 8252 原生应用 OAuth](https://www.rfc-editor.org/info/rfc8252/)

### 解决方案

1. **把 Intent 视作不可信输入**：`route` 只允许公开且必要的目标；拒绝未知路径、控制字符、重复编码、超长参数、任意外部 URL 和由参数拼出的敏感页面。建议外部输入先进入统一解析器，再由 App 自己决定内部路由；不得把原始字符串直接当 Flutter 初始路由。
2. **在页面和接口两处做权限判断**：登录态失效时统一转登录；涉及家庭、日历、设备、支付订单的页面读取和写入都由后端按当前用户与对象关系校验。隐藏页面或路由白名单只能降低暴露，**不能代替服务端对象授权**。
3. **把 OAuth 做成一次性事务**：发起授权时产生高熵 `state` 和 PKCE `code_verifier`，服务器保存 `state`、当前用户、环境、授权提供方、预期 `redirect_uri`、发起时间与待绑定对象；回调时先校验 URI 的 Scheme/Host/Path 与参数格式，再由服务器原子地核对和消费 `state`，带 `code_verifier` 兑换授权码，检查结果属于当前待绑定用户。过期、重复、跨账号、跨环境的回调一律拒绝；回调参数不能直接指定要登录或绑定的用户。
4. **收敛回调分发**：优先使用经过域名验证的 HTTPS Android App Links，并正确部署 `assetlinks.json`。保留自定义 Scheme 时仍必须做 `state`、PKCE 和一次性消费。App Links 降低 Scheme 抢占风险，但不能替代业务校验。[Android App Links 验证](https://developer.android.com/training/app-links/verify-applinks)

### 为什么有效

路由校验使任意 Intent 不能直接选择内部敏感目标；服务端对象授权使攻击者即便显示了页面，也无法读取或修改不属于自己的对象。`state` 将回调与**某次已发起的授权**绑定，防止凭空注入；PKCE 使仅截获授权码而没有本次 `code_verifier` 的人无法兑换；原子消费阻断重复使用。已验证的 HTTPS App Links 增加回调与开发者域名的绑定，降低其他 App 抢占私有 Scheme 的机会。

### 完成判据与边界

- 用外部 App/ADB 发送未知路由、未登录路由、其他用户对象 ID、畸形 URI；客户端拒绝或跳到安全页面，服务器返回未授权且没有对象数据。
- 错误 `state`、错误 PKCE、过期授权码、重复回调、另一测试账号的授权结果及跨环境回调全部被服务端拒绝，账号绑定关系不变化。
- `MainActivity` 是否导出不是核心判据；真正的保证来自输入解析与服务端授权。OAuth 提供方、浏览器和已有老版本客户端的兼容迁移需单独安排。

## 3. 非生产环境和环境切换进入正式包

### 问题原理

假设正式版可通过隐藏菜单或本地偏好切到 `xhome-dev`、`xhome-test`、`xhome-uat`。请求拦截器可能继续附加生产令牌，导致生产身份材料到达隔离程度较低的服务；若不同环境共享发行者、受众或签名密钥，测试系统甚至可能接受生产令牌。APK 中删除地址能减少误用，但攻击者可修改客户端，因此**环境隔离必须由服务端独立强制**。

### 解决方案

1. **分构建产物**：使用独立的 `prod` 与 `dev/test` flavor 和构建配置；正式产物只含生产 API 域名、生产 OAuth 配置及正式证书策略，移除环境切换 UI、持久化键和测试地址。CI 对最终 APK/AAB 的域名和 `Switch environment` 等标记做扫描并失败阻断。`--dart-define` 写入的值仍会进入客户端产物，不可当作秘密。
2. **后端硬隔离**：各环境使用独立用户库或明确分区、令牌发行者 `iss`、受众 `aud`、签名密钥、API Key、OAuth 客户端、回调地址和权限域；每个网关在验证签名后仍校验自己的 `iss`、`aud`、有效期和环境标识。生产网关拒绝测试令牌，测试网关拒绝生产令牌。
3. **限制数据和网络流向**：测试系统禁止接收真实用户敏感数据；生产出口网关或代理仅允许业务域名。若历史上已经混用身份或数据，应检查日志和审计记录，撤销受影响令牌、轮换共享密钥并清理测试数据。

### 为什么有效

分构建产物可以防止正常用户误切环境，并让发布误配置在 CI 阶段暴露；服务端独立的令牌密钥、发行者和受众，使**改写 APK、替换域名或复制令牌**也不能跨环境获得授权。出口限制还能在客户端代码失误时阻断生产凭证送往非生产目的地。

### 完成判据与边界

- 正式产物中无开发/测试/预发域名、切换界面和对应持久化配置；运行时所有正式流程只访问允许的生产域名。
- 生产与测试令牌交叉调用各自网关均被拒；两个环境的 OAuth 回调和用户对象不能串用。
- 仅清除客户端字符串**不能保证**环境安全，必须通过服务端交叉拒绝和流量验证。

## 4. 全体安装包共享对称密钥

### 问题原理

假设 `XHOME_SECRET_KEY` 的同一 AES 密钥被打入所有 APK，且服务端把“能用这个密钥加密/签名”当作可信客户端证明。APK 可被下载、逆向，运行时密钥也会进入进程内存；一人提取密钥便可伪造全体客户端的材料。混淆、把值拆成多段或用 `--dart-define` 注入，只会增加提取成本，**不会改变所有安装包共用秘密的信任缺陷**。对称加密可以保护数据，但共享密钥不能证明具体用户或设备身份。[Android 硬编码密码学秘密](https://developer.android.com/privacy-and-security/risks/hardcoded-cryptographic-secrets)、[Android Keystore](https://developer.android.com/privacy-and-security/keystore)

### 解决方案

1. **先识别密钥用途并制定迁移**：列出该密钥用于传输加密、本地存储、请求签名还是业务数据解密；查清服务器接受它的范围和旧版本兼容窗口。将现有共享密钥按潜在泄露处理，准备轮换、旧协议截止时间和用户升级计划。
2. **传输保密用 TLS，授权靠会话**：不要自行以全局 AES 作为 TLS 或用户认证替代品；服务端按登录态、用户、设备注册状态和目标对象授权。长期服务端密钥留在服务端密钥管理系统，客户端不接触。
3. **本地数据使用每设备密钥**：确需离线加密时，在 Android Keystore 为该安装生成不可导出的设备级密钥，使用具备认证的加密模式（如 AES-GCM），做好密钥失效、卸载/迁移、备份排除和数据重建策略。不要把密文迁移到没有原密钥的新设备后仍期待可解密。
4. **确需设备级请求签名时用非对称方案**：每设备在 Keystore 生成私钥，将公钥经已认证会话注册到服务端；服务器将公钥绑定账号/设备。敏感请求签入规范化的请求方法、路径、正文摘要、服务端挑战、时间和操作 ID；服务器验签、检查挑战一次性使用和对象权限，并支持密钥撤销与轮换。此机制提高私钥复制难度，但被控制的设备仍可能调用签名能力，所以不能替代服务端授权或完整性风控。

### 为什么有效

从协议中删除“全体客户端共用秘密”之后，提取任意一份 APK 不再得到可通用的签名材料。每设备 Keystore 密钥不可导出，泄露半径局限于设备及其当前可执行操作；服务器的挑战和重放缓存使抓到的一份签名不能无限复用。撤销旧共享密钥是关闭原缺陷的关键：**只发布新客户端、但服务器继续接受旧密钥，问题仍存在**。

### 完成判据与边界

- 最终 APK/AAB、构建参数和资源中没有服务器认可的全局共享 AES/HMAC 密钥；服务器在截止日后拒绝全部旧密钥请求。
- 不同设备不能互用本地密钥材料；错误设备签名、重复挑战、改写正文和已撤销设备的请求被拒。
- 设备私钥不等于用户身份；越狱/Root 或恶意进程可能借助当前设备调用密钥，服务端仍须校验用户、对象和风险状态。

## 5. 备份或设备迁移携带会话材料

### 问题原理

Android Auto Backup 默认会考虑 SharedPreferences、内部文件和数据库；如果其中有访问令牌、刷新令牌、设备凭据或可恢复的个人数据，备份/迁移便成为另一条复制路径。即使令牌文件由 Android Keystore 密钥加密，密文被迁移到新设备而密钥未迁移，也会造成恢复失败或异常状态。`allowBackup=false` 是必要的明确意图，但部分 Android 12+ 设备的设备到设备迁移行为不能仅靠它推断。[Android Auto Backup](https://developer.android.com/identity/data/autobackup)

### 解决方案

1. **先按数据分类**：把会话令牌、设备凭据、密钥及其密文、一次性挑战、家庭/日历敏感缓存列为不可备份；可从服务器重建的状态不需要备份。只有确有用户价值的非敏感设置才考虑允许备份。
2. **在存储位置阻断**：会话材料优先放适当的安全存储；临时敏感文件放应用的 `noBackupFilesDir()`，不把秘密写入普通 SharedPreferences、数据库或外部存储。退出登录时删除本地状态并撤销服务器令牌。
3. **同时覆盖平台版本与迁移模式**：在 Manifest 显式声明 `android:allowBackup`；Android 11 及以下用 `android:fullBackupContent`，Android 12+ 且目标 SDK 31+ 用 `android:dataExtractionRules` 分别配置 `<cloud-backup>` 与 `<device-transfer>`。若无需迁移 App 数据，按产品决策关闭或排除所有相关内容；若需迁移，仅用 `<include>` 允许已审核的非敏感文件。针对支持的跨平台迁移能力也核对规则，不能遗漏一种模式。具体 XML 文件路径应以项目真实存储目录为准，不照抄示例文件名。[Android 备份规则与迁移模式](https://developer.android.com/identity/data/autobackup)
4. **服务器处理恢复后身份**：设备更换时走重新登录/设备绑定；刷新令牌按设备绑定并可撤销，旧设备登出或被移除后立即失效。

### 为什么有效

存储到不参与备份的位置或只允许白名单数据参与备份，能阻断备份系统复制认证材料；分别配置云备份和设备迁移，避免“云备份关了，但换机迁移还带走数据”。服务器重新认证使意外恢复出的旧文件也无法自动获得长期访问。

### 完成判据与边界

- Android 7—11、Android 12+ 的云备份和设备迁移各完成一次测试；恢复样本中无令牌、密钥、设备凭据和敏感缓存，且新设备不会自动得到旧会话。
- 对明确允许备份的文件建立清单，新增存储位置须重新审查备份规则。
- 用户主动导出的文件、截图和第三方分享不属于系统备份规则覆盖范围，需要另行管理。

## 6. Google/Firebase Key 可被滥用

### 问题原理

客户端要调用 Google SDK，相关 API Key 往往必须随 APK 发放，因此**不能把“从 APK 提取不出 Key”作为修复目标**。真正的问题是假设 Key 没有限制，任何人拿到字符串都能调用不该开放的 API、消耗额度；或者 Firebase Security Rules 过宽，使知道项目配置的人无需合适身份就能读写数据。Firebase 官方也明确说明：Firebase API Key 通常不是授权秘密，数据授权靠 Security Rules，受支持 API 的滥用防护可结合 App Check。[Firebase API Key 说明](https://firebase.google.com/docs/projects/api-keys)、[Firebase Security Rules](https://firebase.google.com/docs/rules/)

### 解决方案

1. **拆分 Key 的用途**：Android Maps SDK 用独立客户端 Key；Firebase 用仅允许所需 Firebase API 的 Key；服务端 Web Service Key 留在服务器，使用服务端适用的凭据/网络限制，不放入 APK。不要让一个可公开的客户端 Key 同时调用高成本或管理类 API。
2. **设置双重云端限制**：Maps Android Key 限定包名 `com.sdmc.homewoo` 和**实际分发签名证书的 SHA-1**，再限定仅需的 Maps/Places 等 API；多渠道签名分别登记。原报告列出的证书 SHA-256 用于包身份记录，**不能直接填入要求 SHA-1 的 Google Cloud 字段**。对通过 REST 调用的 Google 服务，要核对该 API 是否真的执行 Android 应用限制；无法可靠限制时改由受认证的服务端代理调用。[Google Maps Platform Key 安全指南](https://developers.google.com/maps/api-security-best-practices)
3. **收紧 Firebase 数据权限**：Firestore/Realtime Database/Storage 逐资源写默认拒绝、按 `request.auth.uid` 与对象归属授权的 Security Rules；不依赖客户端页面隐藏或 API Key 保密。支持的服务可启用 App Check 并在观察正常流量后强制执行，同时保留身份和对象权限判断。
4. **控制损失与历史暴露**：设置 API 配额、预算告警、异常来源监控；审计过去调用，必要时在确认新 Key 限制和兼容性后轮换旧 Key。旧 Key 若不再使用应撤销。

### 为什么有效

应用限制把可接受调用收窄到指定包名/签名来源，API 限制使同一个字符串不能调用其他已启用服务；服务端代理把高权限 Key 留在服务器。Security Rules 在 Firebase 服务端执行，即使客户端被修改，也要通过身份和对象关系条件。App Check 提供应用来源信号，但**不能代替用户认证或对象授权**。

### 完成判据与边界

- 云平台显示每个 Key 均有匹配用途的应用和 API 限制；错误包名/签名、非允许 API、旧 Key 的测试请求被拒；真实正式包调用不受影响。
- Firebase 权限测试覆盖未登录、其他用户、越权写入和管理员路径；全部不符合规则的请求被拒。配额与预算告警能触发。
- 包名/证书限制的保护强度取决于具体 Google API 的执行方式；对不能可靠执行的 REST API，必须使用服务端代理与独立授权。

## 7. 网络连接与应用完整性控制不足

### 问题原理

这里按两个实际缺陷都存在处理：一是某些业务流量可能接受明文、错误证书或不可信代理；二是攻击者能把 APK 改包、重签并侧载，服务器仍把它当作官方客户端。TLS 保证连接到经验证的服务器，签名保证官方安装包的完整性，服务端完整性证明提供额外的应用/设备来源信号。三者保护的对象不同。**没有证书 Pinning 本身不等于 TLS 漏洞；有 Pinning 也不等于客户端无法被修改。**[Android 网络安全配置](https://developer.android.com/privacy-and-security/security-config)

### 解决方案

1. **恢复标准 TLS 信任链**：所有业务地址使用 HTTPS；删除跳过证书校验、信任任意证书、正式版信任调试 CA 的代码；在 `networkSecurityConfig` 的 `base-config` 中禁止明文流量，并核对 Flutter/Dart、WebView、原生 SDK 和自定义 Socket 的实际行为。Android 网络策略对原始 Socket 等实现可能只提供尽力而为约束，因此必须结合流量测试。[Android `<application>` 明文流量说明](https://developer.android.com/guide/topics/manifest/application-element.html)
2. **对高价值自控域名评估公钥 Pinning**：如风险评估需要，配置当前与备用公钥、轮换流程和失效演练；必须覆盖实际使用的网络栈。不要为了 Pinning 关闭系统证书校验，也不要在没有备用公钥和更新能力时仓促上线。Pinning 降低某些受信 CA/代理误签场景风险，但无法阻止设备端代码被改写。
3. **识别篡改客户端**：官方渠道分发和签名管理；经 Google Play 分发的高风险操作可使用 Play Integrity 标准请求，由服务器解码并核对包名、签名认可结果、时间/请求细节及 `requestHash` 与实际请求的一致性；非 Play 渠道须有相应的设备/应用注册或风险策略。将结果与用户、会话、操作和一次性挑战绑定，按风险分级拒绝或增加验证。Google 文档要求在服务端校验完整性结果，并建议用 `requestHash` 绑定具体操作。[Play Integrity 标准请求](https://developer.android.com/google/play/integrity/standard)、[结果解读](https://developer.android.com/google/play/integrity/verdicts)
4. **保持服务端最终授权**：所有写操作仍检查用户、对象、金额/设备归属及重放；完整性结果仅是风险信号，不给“官方客户端”自动提升权限。

### 为什么有效

正确的 TLS 校验阻断网络中间人冒充服务器；禁止明文使受支持网络栈不把业务数据裸传。Pinning 对指定域名进一步收窄可接受证书/公钥。Play Integrity 的服务端结果与请求哈希可以发现大量重签、替换包或与验证内容不一致的请求；服务端授权保证绕过完整性检查后仍不能越权。

### 完成判据与边界

- 所有业务流程无明文敏感流量；无效证书、错误主机名、过期证书和仅受测试 CA 信任的证书均不能建立生产业务连接。Pinning 若启用，旧/备用公钥切换演练通过。
- 重签 APK 对高风险接口拿不到符合策略的认可结果；篡改正文、复用完整性结果或把结果用于另一操作的请求被拒。
- 设备被完全控制时仍可能调用真实 App 或绕过客户端检查；完整性策略不是不可伪造的用户身份，也需要处理误判、网络不可用和非 Play 分发用户。

## 8. 非必要敏感权限扩大数据接触面

### 问题原理

Android 权限授予的是**能力**：相机、麦克风、存储等权限一旦授予，App 及进程内的第三方代码在系统允许范围内都可能使用。假设某些权限没有业务必要，保留它们会放大未来代码漏洞、恶意 SDK 或误调用的损失。Manifest 中有权限声明不代表用户已经授予；也不能把扫码、录音等真实需求误判为多余权限。[Android 最小化权限请求](https://developer.android.com/privacy-and-security/minimize-permission-requests)

### 解决方案

1. **建立权限与功能映射**：逐项列出权限、触发页面、功能负责人、SDK 来源、支持的最低/最高 Android 版本和没有权限时的替代路径。先删除没有明确功能依据的声明；检查最终**合并后的 Manifest**，因为 Flutter 插件和三方 SDK 可能重新加入权限。
2. **用能力更窄的系统组件**：从相册选取二维码图片优先用系统 Photo Picker，避免申请整库读取；相机扫码保留相机权限但只在进入扫码流程时请求；录音只在用户主动启用语音功能时请求，停止后释放录音资源。支付、生物识别和通知按具体 SDK/API 要求核对，不按名字一概删除。[Android Photo Picker](https://developer.android.com/training/data-storage/shared/photo-picker)
3. **分版本收敛旧权限**：复核 `READ_EXTERNAL_STORAGE` 和仅适用于旧系统的 `WRITE_EXTERNAL_STORAGE` 是否仍由功能实际需要；能迁移至 Photo Picker/系统文档选择器/分区存储的功能就移除宽泛权限。对确需保留的旧版声明设置正确的 `maxSdkVersion`，并测试 minSdk 24 到当前目标平台的行为。
4. **按场景请求并处理拒绝**：危险权限在用户触发功能时解释用途并请求；拒绝后提供可理解的降级，不反复弹窗或阻断不相关功能。依赖升级时重新审查 Manifest 变化。[Android 运行时权限指南](https://developer.android.com/training/permissions/requesting)

### 为什么有效

未声明的权限无法被系统授予；Photo Picker 只给用户选中的媒体访问权，缩小了整库暴露范围。运行时按需请求减少长期授权和用户误授权；拒绝后降级使应用不必为了启动而提前索取所有能力。合并 Manifest 检查防止插件更新悄悄把权限加回来。

### 完成判据与边界

- 最终 APK 的权限列表每一项都有功能依据；未使用的存储/相机/录音权限已移除，必要权限只在相关功能触发时请求。
- 用户拒绝或撤销权限后，相关功能安全失败，其他功能仍可使用；从 Android 7 到目标版本的兼容路径均已验证。
- 最小权限降低潜在损失，但不能代替对实际使用相机、麦克风或媒体数据的代码和第三方 SDK 审查。

## 实施顺序与发布门槛

| 阶段 | 先做什么 | 原因 | 放行条件 |
|---|---|---|---|
| 紧急控制 | 停止敏感日志；核查/撤销已暴露令牌；限制 Google Key；关闭可疑非生产入口 | 先切断持续泄露与额度消耗 | 新日志无秘密，旧凭证处置完成，Key 有用途限制 |
| 身份边界 | 修复 OAuth 事务与对象授权；隔离环境令牌；淘汰共享密钥 | 这些问题一旦成立会直接影响账号和业务数据 | 伪造/重放/跨账号/跨环境请求均被服务端拒绝 |
| 设备与分发 | 收敛备份、TLS、完整性和权限 | 降低本地复制、仿冒客户端与设备数据暴露 | 备份/迁移、证书、重签包和权限矩阵通过测试 |
| 每次发布 | 检查最终 APK/AAB、云端配置和服务端拒绝规则 | 修复不能只存在于源码分支或文档中 | 自动检查和人工复核均有记录与负责人 |

**最重要的验收原则**：只看“代码已提交”不足以关闭问题。每一项都要在**正式构建产物**、相应服务器或云平台配置以及攻击反例测试中同时得到证据。若某项控制依赖旧版客户端升级，应记录旧协议停用日期和灰度策略；服务器在停用日期后继续接受旧行为，就不能认定该问题已经消除。
