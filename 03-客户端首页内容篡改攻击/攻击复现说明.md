# Homewoo APK 二次打包：登录后替换首页

> 仅用于已授权的内部安全测试、漏洞验证和防护演示。本文不保存账号、密码、Token 或签名私钥口令。

## 攻击目标与范围

验证攻击者能否在授权测试 APK 中植入自定义首页，并在用户登录后覆盖原 Homewoo 首页。范围仅包括测试 APK、Root 测试设备、测试账号和本机测试落地页，不连接生产服务或第三方网站。

### 1. 实验目标

使用原始 APK 二次打包一个测试版本，使行为变为：

```text
登录页 → 登录成功 → 自定义首页
```

自定义首页必须覆盖原 Homewoo 首页；重新打开 App 后，如果本地登录态仍然存在，也必须继续显示自定义首页。

原始 APK：`../app-arm64-v8a-release.apk`

最终验证包：

`artifacts/homewoo-custom-home-repackaged-v8.apk`

### 0.1 统一攻击摘要

## 前置条件

- 原始 Homewoo APK；
- Root Android 测试设备和 ADB；
- JDK、apktool、Android SDK Build Tools；
- 本地测试签名 keystore；
- 已获授权的测试账号和测试数据；
- 测试人员可在手机上手工完成登录。

## 攻击手段

攻击者解包原 APK，加入自定义 Java 页面和登录态观察逻辑，修改 `MainActivity.smali` 后重新打包、对齐并签名。登录态出现后，在原 Activity 的内容层覆盖完整自定义首页，不依赖原 Homewoo 首页继续展示。

## 攻击获得信息

- 本地登录态是否存在；
- App 包名、Activity、存储文件名和页面生命周期信息；
- 用户登录后可看到的客户端页面和业务上下文；
- 若继续扩展注入代码，还可能获取用户在伪造页面中输入的密码、验证码、Token 或其他敏感信息。

## 攻击流程和操作

1. 准备原始 APK、Root 测试机和构建工具；
2. 执行构建脚本生成 `homewoo-custom-home-repackaged-v8.apk`；
3. 卸载原测试包并安装篡改包；
4. 在手机上手工登录；
5. 检查 UI dump 和 logcat，确认登录后出现自定义首页；
6. 强制停止并重新启动 App，确认保留登录态时仍显示自定义首页；
7. 点击“打开测试落地页”，确认篡改页面可以引导用户进入本机测试页面。

## 工具、脚本和参数

- 主流程：`run_custom_home_attack.sh`；构建子流程：`build_custom_home_attack.sh`；注入脚本：`inject_custom_home.py`；Java 组件位于 `src/`；本机落地页：`scripts/local_landing_server.py`；
- 参数：`preflight`、`build`、`mock`、`install`、`clean-install`、`verify`、`verify-signature`、`verify-landing`、`reopen`、`verify-original`、`restore-original`；
- 外跳验证：`verify-landing` 会通过 UIAutomator 点击篡改首页的“打开测试落地页”按钮，再检查本机服务收到 `/test-landing` 请求；
- 测试页面通过 `adb reverse tcp:18080 tcp:18080` 访问本机服务，不访问真实第三方网站。

## 攻击成功判据

必须同时满足设备安装的 APK 与归档 v8 包哈希一致、当前 Activity 为 Homewoo 主页面、登录后 UI 出现三个自定义文本、重新启动后仍显示自定义首页，且验证脚本返回成功。`HomewooRedirect` 日志为辅助证据；设备未输出该日志时不单独判失败。

## 实际验证结果

2026-10-12 23:28—23:29（CST）在 Root Redmi Note 7 上安装 v8，设备包与归档包 SHA-256 均为 `054f9d49fa30db0f38ecf5666850ec971f2e4bc0323181658a64194c32958858`。保留原有登录态执行 `verify` 和 `reopen` 均返回 `VERIFY_PASSED=true`；执行 `verify-landing` 后，点击自定义首页按钮使本机服务收到 `/test-landing` 请求，返回 `VERIFY_LANDING_PASSED=true`。

本次证据：`evidence/ui-20261012-232853.xml`、`evidence/ui-20261012-232904.xml`、对应的 `activity-*.txt`、`evidence/apk-sha256.txt`、`evidence/landing.log`。设备没有输出 `HomewooRedirect` 日志，日志文件为空；本次成功判据使用设备包哈希、Activity、UI 标记和按钮触发的本机请求。

随后执行 `restore-original`，原始 APK 签名校验和原始登录页标记检查通过，脚本输出 `RESTORE_VERIFIED=true`。该命令会清除测试包本地登录态。测试机需要使用 Root 执行模拟点击；`verify-landing` 已按此修正并现场通过。

独立复核指出：23:28—23:29 的旧脚本只把部分关键结果打印到终端，未把设备端哈希、`reopen` 命令结果、按钮点击结果和恢复结果完整写入 `evidence/`，因此这些文件尚不足以让另一位测试人员独立重建完整操作链。主脚本现已增加 `verify-*.txt`、`reopen-*.txt`、`landing-verify-*.txt` 和 `restore-*.txt` 的自动留存；这些新摘要文件必须在下次登录后重新执行相应命令才会产生。本次保留的现场记录见 `evidence/现场验证记录-20261012.md`，不替代缺失的原始命令证据。

## 可能造成的后果

攻击者可能伪造首页、公告、业务入口，诱导用户在仿冒页面输入密码、验证码或其他敏感信息，造成品牌冒用和业务风险。

## 防护方案

启用应用完整性和证书校验、Play Integrity、Root/调试环境风险识别；关键业务状态由服务端确认，并对异常客户端和外跳行为进行风控。

## 清理和恢复

执行 `./run_custom_home_attack.sh restore-original` 卸载篡改包、安装原始 APK、校验签名并确认原始页面标记。

## 局限和未验证事项

本次复用了设备已有登录态，未重新输入账号密码走一遍新登录；完整命令证据仍需按新版脚本重跑。原始 APK 无源码、非 Root 设备、iOS IPA 和生产环境均未验证。

### 3. 攻击原理

原包没有提供源码，本实验采用 APK-only 二次打包：

1. 使用 apktool 解包原 APK；
2. 在 Manifest 中加入测试 Activity，并加入测试主题；
3. 编译 `CustomHomeActivity.java` 和 `RedirectWatcher.java`；
4. 将编译后的 `classes2.dex` 合入 APK；
5. 修改 `MainActivity.smali` 的 `m()` 方法，在 Flutter 页面初始化阶段启动状态观察器；
6. 观察 `FlutterSecureStorage` 的条目数量，作为“已完成登录”的实验判据；
7. 登录态出现后，在当前 `MainActivity` 的 `android.R.id.content` 内容层加入全屏自定义 View，直接覆盖 Flutter 页面。

关键点是“内容层覆盖”，而不是启动一个新的 Activity。旧版本启动 `CustomHomeActivity` 时，Flutter 原页面已经绘制，且原 Activity 可能重新回到前台，所以会出现“原首页 → 自定义首页”或再次回到原首页。

### 7. 安装和验证

### 7.1 首次安装

首次安装会清除原包数据，必须重新手工登录：

```bash
cd "03-客户端首页内容篡改攻击"

  "../app-arm64-v8a-release.apk" \
  "$PWD/artifacts/homewoo-custom-home-repackaged-v8.apk"
```

在手机上手工完成登录。登录成功后使用：

```bash
./run_custom_home_attack.sh verify
```

预期结果：UI dump 能找到 `自定义首页`、`登录成功后替换原 Homewoo 首页`、`打开测试落地页`，日志能找到 `overlaying MainActivity with CustomHomeView`。

启动本机落地页后，可使用以下脚本验证按钮目标：

```bash
./run_custom_home_attack.sh verify-landing
```

### 7.2 验证“再次进入 App”

不要卸载 App，直接重启进程：

```bash
./run_custom_home_attack.sh reopen
```

只要登录态仍然存在，预期仍能找到自定义首页文本。v8 构建后应完成该验证。

### 7.3 保留登录态更新测试包

如果只是更新脚本生成的同一测试签名 APK，可使用：

```bash
./run_custom_home_attack.sh install
```

这样不会主动清除应用数据；如果出现签名不一致或安装失败，先卸载旧测试包再安装，并重新登录。

### 8. 旧版本问题和修复

### v2/v3：独立 Activity 跳转

检测到登录态后启动 `CustomHomeActivity`。问题是原 Flutter 首页已经绘制，且 `MainActivity` 仍在任务栈中，可能重新回到前台。

### v4：增加 `CLEAR_TASK`

尝试清除原任务栈，但仍属于 Activity 切换，不能消除 Flutter 首页已经出现的时间窗口。

### v5：改为内容层覆盖

解决了 Activity 竞争问题，但保存了 `shown=true`。第二次启动时这个标记阻止了再次覆盖，所以又看到原首页。

### v6：去掉持久化 `shown` 标记

每次观察器启动都按当前登录态判断；登录态存在就覆盖当前 MainActivity 内容层，已验证重新进入 App 仍显示自定义首页。

### v7：移除返回原首页按钮

删除“返回原 Homewoo”操作，改为“打开测试落地页”。

### v8：改为本机测试落地页

按钮通过 `Intent.ACTION_VIEW` 打开 `http://127.0.0.1:18080/test-landing`，由 `adb reverse` 转发到本机 `local_landing_server.py`，不访问第三方网站。

### 9. 安全影响

该实验说明：如果攻击者能取得可运行 APK 并完成二次签名、诱导用户安装篡改包，就可以在登录后的客户端界面植入完全自定义的页面。可能造成：

- 用户误以为仍在使用原 App；
- 首页展示虚假业务信息、公告、活动或收款入口；
- 引导用户输入二次密码、验证码、支付信息或企业敏感数据；
- 在自定义页面继续加入数据采集、远程控制或恶意跳转逻辑；
- 破坏品牌信任，并造成账号、业务数据和合规风险。

### 10. 防护建议

- 启用 Play Integrity / App Attest 等设备和应用完整性校验；
- 服务端校验包签名、证书摘要和版本，不把“登录成功”仅作为客户端可信信号；
- 对关键接口使用服务端授权、短时 Token、重放防护和风险控制；
- 对高风险操作增加服务端二次确认，不信任客户端展示结果；
- 对 Root、调试、Frida、Xposed、模拟器和异常证书环境进行风险标记；
- 对安装包启用签名保护、完整性校验和发布渠道监控；
- 对登录后首页展示的关键数据做服务端签名或完整性校验；
- 定期使用本目录脚本验证“二次打包后是否仍能通过登录并展示伪造页面”。
