# 攻击一：接口日志泄露与请求重放攻击

### 0. 快速开始

在确认使用授权测试账号和测试数据后：

```bash
cd "/Users/h1610/Desktop/安全方案/01-接口日志泄露与请求重放攻击"
adb devices
adb shell su -c id
```

在 App 中先进入 Calendar 页面，完成一次目标操作，再执行：

```bash
./run_replay_attack.sh list
```

新增、编辑或删除测试事件后，分别执行：

```bash
./run_replay_attack.sh create
./run_replay_attack.sh update
./run_replay_attack.sh delete
```

脚本输出 HTTP 状态和业务返回码即表示请求已发出；数据是否改变还要再次在 App 或 `list` 查询中核对。

## 攻击目标与范围

在授权测试账号、测试设备和测试环境中，验证 App 将接口请求材料写入日志后，攻击者能否在 App 外重放合法请求。范围仅包括测试账号的日历对象，不涉及生产数据、跨账号访问或真实用户。

测试端点默认是 `https://xhome-dev.sdmc.tv:18443/aihome/cloud-api/awp`，仅允许在已授权的开发/测试环境使用；如需切换，必须通过 `HOMEWOO_TEST_BASE` 环境变量显式提供测试端点。

测试输入 APK：`../app-arm64-v8a-release.apk`；SHA-256：`968460c42b849e0b91f2a1de46a8c1c18a12027066251aaaac190267c8545c38`。

### 0.1 统一攻击摘要

## 前置条件

- 已获授权的测试 APK、测试账号和测试数据；
- Root Android 测试设备和可用 ADB；
- App 已登录，并且目标日历操作已经在 App 中触发过；
- `logcat` 中仍保留包含请求材料的日志；
- 主机具备 Python 3 和访问测试环境的网络能力。

## 攻击手段

攻击者读取设备日志中由 App 输出的接口请求，提取合法请求体、请求头、Token 和签名，在 App 外使用脚本原样重放，不需要破解 TLS 或重新生成签名。

## 攻击获得信息

- 当前账号相关的日历列表、事件 ID、标题、时间和返回结果；
- 接口路径、请求方法、请求体、必要请求头；
- 在日志中暴露的 AccessToken、签名和设备/版本信息；
- 通过重放获得的新增、编辑、删除接口响应。

## 攻击流程和操作

1. 登录测试 App 并触发一次读取、新增、编辑或删除；
2. 从 `logcat` 中定位目标请求；
3. 提取原始请求材料；
4. 执行 `./run_replay_attack.sh list|create|update|delete`，自动在 `evidence/` 保存脱敏结果；
5. 分别保存攻击前后的 `list` 结果；
6. 执行 `./run_replay_attack.sh compare create <before.json> <after.json>`，或 `./run_replay_attack.sh compare update|delete <before.json> <after.json> <event_id>`，确认测试对象状态发生变化；其中 `create` 的前后文件应为操作前后的 `list` 脱敏证据。

## 工具、脚本和参数

- 主流程：`run_replay_attack.sh`；子脚本：`scripts/homewoo_calendar_replay.py`、`scripts/verify_replay_result.py`；
- 参数：`preflight`、`list`、`create`、`update`、`delete`、`verify`、`compare`、`cleanup`、`restore-original`；
- 脚本从设备日志提取请求，仅输出脱敏状态和结果，不落盘完整 Token、签名或请求体。

## 攻击成功判据

HTTP 成功只代表服务端接受请求；必须结合返回业务码和测试对象前后对比，才能认定读取、新增、编辑或删除成功。

## 实际验证结果

历史运行记录显示读取、新增和编辑请求曾被 App 外脚本重放；删除接口曾返回成功，但删除动作的独立因果关系仍需使用专用测试对象再次验证。本目录当前未保存对应运行证据，重新执行后以 `evidence/` 为准。

## 可能造成的后果

攻击者可能利用日志中的合法会话读取、篡改或删除测试账号可访问的日历数据，造成隐私泄露、业务数据破坏和审计风险。

## 防护方案

禁止敏感请求写入 logcat；服务端增加时间戳、Nonce、重放记录、短时 Token 和服务端授权校验，并对关键写操作做二次确认。

## 清理和恢复

执行 `./run_replay_attack.sh restore-original` 清理设备日志；服务端测试事件、测试账号和临时抓包文件按本报告说明手工清理。

## 局限和未验证事项

当前目录未保存本次运行证据；普通未 Root 设备、跨账号访问和删除动作的独立因果关系未在本次静态整改中重新验证。

### 1. 攻击结论

这是第一条独立攻击链：App 将接口请求材料写入 logcat，攻击者从日志获取合法请求后，在 App 外重放。

历史运行记录（非本目录当前证据）：

- 日历读取成功；
- 日历新增成功；
- 日历编辑成功；
- 删除接口返回成功，但删除动作的独立因果关系尚未完全证明；
- 修改请求体后复用旧签名返回 HTTP 401。

### 2. 前置条件

- 已获授权的测试 APK、测试账号和测试数据；
- Root Android 测试设备；
- macOS/Linux 主机；
- `adb`、Python 3、网络访问能力；
- App 已登录，并且目标操作已经在 App 中触发过；
- 当前 `logcat` 仍保留请求日志。

不得使用生产账号或真实重要日程。

### 3. 工具结构

```text
run_replay_attack.sh                 主流程入口
scripts/homewoo_calendar_replay.py  日志解析和请求重放子脚本
```

主流程负责设备检查和动作路由，子脚本负责：

1. 读取当前设备 `logcat`；
2. 定位目标接口日志；
3. 提取请求体和必要请求头；
4. 向测试接口发送原始请求；
5. 只输出状态码、返回码和事件数量等非敏感结果。

### 4. 执行步骤

### 4.1 连接并确认设备

```bash
adb devices
adb shell su -c id
```

输出应包含 `uid=0(root)`。

### 4.2 读取日历

先在 App 中进入日历页面，确保产生列表请求，然后执行：

```bash
./run_replay_attack.sh list
```

预期结果：

```text
ACTION=list
HTTP_STATUS=200
RETURN_CODE=200
EVENT_COUNT=...
```

### 4.3 新增日历

在 App 中新增一条测试事件，确保日志出现完整 create 请求，再执行：

```bash
./run_replay_attack.sh create
```

预期包含：

```text
HTTP_STATUS=200
RETURN_CODE=200
EVENT_ID_PRESENT=True
```

### 4.4 编辑日历

在 App 中编辑同一测试事件后执行：

```bash
./run_replay_attack.sh update
```

再执行 `list` 核对标题是否变化。

### 4.5 删除日历

只对专用测试事件执行：

```bash
./run_replay_attack.sh delete
```

HTTP 200 只能证明服务端接受请求；必须前后查询同一对象，才能证明删除状态变化由脚本造成。

### 5. 信息边界

脚本会在内存中读取日志里的访问令牌、签名和请求体，但不把它们写入文件，也不打印完整敏感值。密码不经过脚本处理，由测试人员在设备上手工输入。

### 6. 影响

攻击者可能读取家庭日历、添加虚假安排、修改重要事件、诱导用户错过行程，进一步推断家庭关系和活动规律。

### 7. 清理和恢复

`restore-original` 只清理设备日志；本攻击不改写 APK，因此没有客户端包需要回滚。它不会替服务端删除已创建的测试日历数据，也不声称能够证明请求来自哪个 APK。服务端业务数据必须依据前后证据，由测试人员使用 App 或授权管理接口手工删除并再次执行 `list` 确认。

测试人员需另行手工删除测试事件、修改测试账号密码、撤销测试会话，并清理临时抓包文件；主流程的 `restore-original` 仅清理设备日志。

### 8. 攻击原理

正常情况下，客户端应该只负责发起业务请求，服务端负责鉴权、对象归属校验和业务变更。本次测试发现，App 把服务端接受请求所需的材料打印到了设备日志中：

```text
App 生成请求
    ├── URL
    ├── 请求体
    ├── accessToken
    ├── signature
    └── timestamp
          ↓
       logcat
          ↓
攻击脚本读取日志
          ↓
在 App 外重新发送原请求
          ↓
服务端将其视为合法请求
```

攻击者不需要破解 TLS，也不需要知道签名算法。因为 App 已经生成了服务端认可的完整请求，攻击者只需要复制并重放。

### 9. 请求重放的内部过程

### 9.1 日志解析

`homewoo_calendar_replay.py` 使用 `adb logcat` 读取当前日志，然后按接口路径筛选最近一段完整请求。它只处理以下四个接口：

```text
/calendar/event/list
/calendar/event/create
/calendar/event/update
/calendar/event/delete
```

### 9.2 请求恢复

脚本从日志恢复：

```text
接口路径
请求体 JSON
signature
accessToken
timestamp
clientId
设备和版本信息
```

然后将原始请求体重新发送到测试环境。脚本不会修改请求体，因此旧签名仍然有效。

### 9.3 服务端为什么接受

服务端通常会校验：

```text
签名是否正确
Token 是否有效
时间戳是否在有效期内
请求体是否与签名一致
```

本次重放使用的是 App 原本生成的完整请求，所以这些校验仍然能够通过。签名可以防止“篡改请求”，但不能单独防止“复制合法请求”。

### 10. 四类业务动作的证明方式

### 10.1 list：读取

证明点是脚本能够在 App 外获得与当前账号相关的日历事件数量和返回结果。

```text
App 日志中的 list 请求
        ↓
脚本重放
        ↓
HTTP 200 / RETURN_CODE=200
        ↓
EVENT_COUNT
```

### 10.2 create：新增

先在 App 中创建一个专用测试事件，再从日志提取 create 请求。脚本重放后检查返回的 `eventId`，随后再次执行 list，确认数量或事件内容变化。

### 10.3 update：编辑

先在 App 中编辑专用测试事件，再重放 update 请求。成功判据不是 HTTP 200 alone，而是再次 list 后标题、时间或描述发生预期变化。

### 10.4 delete：删除

删除必须进行前后对照：

```text
list：对象存在
→ 脚本 delete
→ list：对象不存在
```

如果对象在脚本执行前已经被 App 删除，只能记录“接口返回成功”，不能记录“脚本删除成功”。

### 11. 证据链

每次测试至少保留以下非敏感证据：

```text
测试时间
接口动作
HTTP_STATUS
RETURN_CODE
EVENT_COUNT 或 EVENT_ID_PRESENT
测试对象的非敏感标题
```

不要保存以下内容：

```text
明文密码
完整 AccessToken
完整 Cookie
完整 signature
完整个人日历响应
```

### 12. 攻击成功与否的判断

```text
能够读取日志             = 准备条件成立
脚本返回 HTTP 200        = 请求被服务端接受
业务数据实际变化         = 对应业务攻击成功
修改请求体后旧签名失效   = 完整性校验有效，但不等于防重放
```

### 13. 局限和未验证事项

- 未证明普通未 Root Android 应用可以读取全部日志；
- 未验证跨账号对象访问；
- 未证明攻击者可以自行生成新签名；
- 删除动作需要独立因果验证；
- 测试只针对授权测试账号和测试环境。
