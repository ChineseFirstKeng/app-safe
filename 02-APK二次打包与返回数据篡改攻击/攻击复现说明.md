## 攻击目标与范围

验证攻击者能否修改授权测试 APK 的接口地址，通过本地或授权测试网络 Mock 返回结构合法但内容伪造的日历数据。范围仅包括测试 APK、测试账号、测试设备和测试 Mock，不连接生产服务。

### 0.1 统一攻击摘要

## 前置条件

- 原始 Homewoo APK；
- Root Android 测试设备和 ADB；
- JDK、Python 3、apktool、`zipalign`、`apksigner`；
- 本地或局域网 Mock 服务；
- 测试签名密钥；
- 手机和 Mock 主机处于同一测试网络；
- 只使用授权测试账号和测试数据。

## 攻击手段

解包原 APK，修改 Flutter AOT 中的接口地址，重新打包、对齐并使用攻击者控制的测试签名重新签名；篡改包把请求发送到 Mock 服务，由 Mock 返回结构合法但内容伪造的业务数据。

## 攻击获得信息

- 篡改包运行期间经过 Mock 的登录和业务请求；
- 原接口路径、请求方法、请求体结构和响应结构；
- 测试环境中的登录结果及日历接口返回内容；
- 可被伪造展示的事件标题、时间、ID 和业务状态。

## 攻击流程和操作

1. 启动 `./run_repackaging_attack.sh mock`；
2. 使用 `./run_repackaging_attack.sh build` 生成二次打包 APK，或直接使用现有产物；
3. 使用 `./run_repackaging_attack.sh install` 安装；
4. 在手机上手工登录并进入 Calendar；
5. 执行 `./run_repackaging_attack.sh verify`，确认页面出现 `TAMPERED_BY_REPACKAGED_APP`；
6. 对比原包和篡改包的接口地址、响应内容和页面展示。

## 工具、脚本和参数

- 主流程：`run_repackaging_attack.sh`；子脚本负责 URL 修改、构建签名和 Mock 响应；
- 参数：`preflight`、`mock`、`build`、`install`、`clean-install`、`verify`、`verify-signature`、`restore-original`；
- Mock 默认仅绑定 `127.0.0.1`，非目标请求默认阻断；只有明确设置 `ALLOW_UPSTREAM_PROXY=1` 才允许转发到声明的开发测试端点。
- 如需转发非目标接口，必须显式设置 `UPSTREAM_TEST_BASE=https://xhome-dev.sdmc.tv:18443`；Mock 会拒绝其他主机、端口或明文 HTTP 目标。

## 攻击成功判据

必须同时满足 APK 安装启动成功、Mock 收到目标请求、UI dump 中出现 `TAMPERED_BY_REPACKAGED_APP`，且验证脚本返回非零失败/零成功的明确结果。

## 可能造成的后果

攻击者可能伪造日历、公告、业务状态和跳转入口，诱导用户泄露账号或敏感信息，造成品牌冒用和业务判断错误。

## 防护方案

启用应用完整性和证书校验、Play Integrity、服务端风险识别；关键业务状态必须由服务端确认，不能信任客户端改写后的响应。

## 清理和恢复

执行 `./run_repackaging_attack.sh restore-original` 恢复原始 APK、校验签名并确认原始页面标记；服务端测试数据仍需手工清理。

### 12. 攻击原理

APK 二次打包攻击的核心不是“修改服务端”，而是修改客户端，使客户端把请求发送到攻击者控制的地址：

```text
原始 Homewoo APK
    ↓ 解包
libapp.so
    ↓ 替换接口基地址
http://192.168.68.84:18443
    ↓ 重新打包、对齐、签名
篡改后的 Homewoo APK
    ↓ 安装并登录
本机/局域网 Mock 服务
    ├── 登录、家庭信息等非目标请求 → 转发测试环境
    └── 日历列表请求             → 返回伪造响应
```

原 App 的包名和业务代码仍然存在，所以用户看到的仍是 Homewoo 页面；区别是网络请求已经不再完全由原服务端控制。

### 13. 为什么只修改 URL 就能生效

Homewoo 使用 Flutter AOT，运行时网络基地址被编译进 `libapp.so`。脚本执行以下操作：

1. 在二进制中定位原始开发环境 URL；
2. 将其替换为测试 Mock 地址；
3. 用斜杠填充剩余长度，避免破坏二进制内部偏移；
4. 重新封装 APK；
5. 对 native 库进行对齐；
6. 使用测试密钥重新签名。

修改后，App 不知道自己被替换过，仍按原有代码拼接 `/aihome/cloud-api/...` 路径，因此请求会到达新的基地址。

### 14. Mock 服务的数据流

```text
篡改 App
   │ POST /aihome/cloud-api/cloud/v5.0/user/login
   │ POST /aihome/cloud-api/awp/home/count
   │ POST /aihome/cloud-api/awp/calendar/event/list
   ▼
Mock 服务
   ├── 非目标接口：保留请求头和请求体，转发到测试环境
   └── calendar/event/list：不转发，直接构造 JSON
                         ↓
                TAMPERED_BY_REPACKAGED_APP
                         ↓
                    Homewoo 页面
```

这样做的目的是让 App 能正常登录和进入页面，同时只对一个明确的日历接口进行篡改，便于证明因果关系。

### 15. 为什么返回数据必须符合原接口结构

客户端不会接受任意 JSON。它会按照原有日历模型读取字段，例如：

```text
returnCode
data.events
eventId
instanceId
title
startTime
endTime
timezone
participantProfileIds
```

如果字段缺失、时间单位错误或事件不在当前显示周内，可能出现“请求和篡改成功，但页面显示 No event”。因此 Mock 响应必须同时满足：

1. JSON 结构符合客户端模型；
2. 时间戳落在当前页面的日期范围内；
3. 事件包含客户端渲染所需字段；
4. `returnCode` 表示成功。

### 16. 二次打包攻击的成功判据

必须同时满足以下条件，才能记录为完整成功：

```text
APK 安装成功
→ App 能启动
→ 用户能登录
→ Mock 收到目标接口请求
→ Mock 返回伪造数据
→ App 日志或页面能看到伪造内容
```

只有“APK 能安装”或“Mock 收到请求”，不能单独证明业务篡改成功。

### 17. 防护缺口对应关系

| 攻击步骤 | 说明 | 应关注的防护 |
|---|---|---|
| 修改 APK | 客户端完整性被破坏 | Play Integrity、签名校验、反篡改、运行环境检测 |
| 重定向接口 | 客户端可控制服务地址 | HTTPS、证书校验、证书绑定、服务端环境隔离 |
| 伪造返回 | 客户端信任本地响应 | 服务端状态为最终事实，关键结果二次校验 |
| 篡改页面 | 用户看到虚假业务状态 | 风险操作服务端确认、审计和异常客户端检测 |
